# ADR-RN-016: Genesis Proof 01 anchoring transactions and execution controls

- Status: Accepted (founder approval of PR #10 as implemented, RN-NET-03B2-A acceptance)
- Date: 2026-11-01
- Amendment C1: **Accepted for the reviewed offline implementation only** (recorded when the founder merges this documentation change; the implementation is RN-NET-03B2-C3, PR #26, squash-merged as main `1723439`, whose tree `a91fc55` equals the reviewed head `578a4db`). It accepts the `+ 80` expiry as the binding rule of the reviewed offline preparation code. It authorizes no live RPC, no key generation, funding, signing or broadcasting, and no publication.
- Builds on: [ADR-RN-009](ADR-RN-009-anchor-payload-encoding.md), [ADR-RN-010](ADR-RN-010-xrpl-testnet-memo-anchoring.md), [ADR-RN-011](ADR-RN-011-sepolia-transaction-data-anchoring.md), [ADR-RN-012](ADR-RN-012-cross-chain-trust-boundaries.md)
- Design: [Genesis Proof 01 preflight](../genesis/genesis-proof-01-preflight.md), [authorization](../genesis/genesis-proof-01-authorization.md)

## Context

Genesis Proof 01 is the first real dual-chain anchor: one commitment, one XRPL Testnet
transaction and one Sepolia transaction. ADR-RN-010 and ADR-RN-011 define what an anchor *looks
like* to a verifier, and they accept many transactions. Signing a real transaction means fixing one
exact construction, its costs, and the controls around keys and broadcasting. All of these are
irreversible once a transaction is public.

This ADR changes no format: the payload, the observation, the record and the report stay as they
are.

## Decision

1. **The XRPL transaction.** An unsigned `AccountSet` with exactly these fields:
   - `TransactionType`, `Account`, `Fee`, `Sequence`, `LastLedgerSequence` and `Memos`, plus
     `SigningPubKey` at signing time;
   - `Memos` holding exactly one anchor memo (`MemoType` = hex(`rnnet.anchor-payload.v1`),
     `MemoData` = the payload, no `MemoFormat`);
   - no `NetworkID` (Testnet's ID is 1), no `Flags` (or 0) and no settings fields.

   Other details:
   - **Fee:** 12 drops, with a hard cap of 1,000.
   - **Expiry:** `LastLedgerSequence` is required, set to the latest validated ledger + 20.
   - **Key:** an Ed25519 key.
2. **The Sepolia transaction.** An unsigned EIP-1559 (type `0x2`) transaction with:
   - chain ID `0xaa36a7`;
   - value 0 and an empty access list;
   - `input` exactly the 42-byte payload;
   - **sent to its own sender (a self-send).**

   Gas and fees:
   - **Gas limit:** 30,000. The intrinsic cost under Prague rules is 22,680. Unused gas costs
     nothing.
   - **maxFeePerGas:** 2 × the base fee + tip, never above 20 gwei.
   - **Priority fee:** 1 gwei.

   **Why a self-send.** A self-send involves no third-party address. The recipient is an account
   with no code, so nothing executes, and the sender is the only address involved. As in
   ADR-RN-012, the submitter stays a `CLAIMED` value.
   The sender must be a fresh key with no EIP-7702 delegation, so that it still has no code.
3. **The checks are executable.** The construction is pinned as code in
   `tools/genesis/prepare.mjs`:
   - `checkXrplAnchorTx` and `checkSepoliaAnchorTx` refuse every other construction;
   - an unbound template fails them.

   A transaction may be signed only if its check returns no problems. The checks accept only
   plain JSON data, and what is signed must be exactly the canonical JSON of the object that was
   checked.
4. **Separate decisions for keys, funding, signing and broadcasting.** Each step that touches a
   key, an account, funds or a network write needs its own founder decision (gates B–F of the
   authorization document). No approval carries over to another step or another network.
5. **Key hygiene.**
   - **New keys only.** Keys are new and single-purpose: one per network, testnet only.
   - **Generation.** Keys are generated by reviewed RN-NET code inside a network namespace.
   - **Storage.** Keys are never stored in a repository or worktree.
   - **No reuse.** Keys are never reused, and never derived from material any other project
     uses. This includes Frontera and Soberanía credentials, accounts and wallets.
   - **Signing and broadcasting stay apart.** Signing happens offline. Broadcasting is done by a
     process that never holds a key.

## Consequences

- **Small, fixed costs.** At most 1,000 drops on XRPL. On Sepolia, at most 30,000 × 20 gwei =
  0.0006 ETH. Expected costs are much lower (see the preflight document).
- **Tooling RN-NET-03B2-B must add:**
  - signing;
  - a write path (`submit`, `eth_sendRawTransaction`);
  - a few read-only methods: XRPL `account_info`; Ethereum `eth_getTransactionCount`,
    `eth_estimateGas`, `eth_getBalance` and `eth_getCode`.

  Each needs review, and the write path needs its own ADR. `packages/chain-readonly` stays
  read-only.
- **Open decision for RN-NET-03B2-B: the Sepolia signer dependency.** Node.js built-ins have no
  Keccak-256, and `crypto.sign` always hashes its input, so they cannot produce a recoverable
  secp256k1 signature over a Keccak-256 digest. RN-NET-03B2-B must choose, in its own ADR:
  - an audited third-party library, pinned like the existing development dependency;
  - or an original implementation, checked against published test vectors.

  Accepting this ADR does not make that choice. The XRPL signer needs no new dependency.
- **What this acceptance covers.** It accepts the construction and controls above. It does not
  accept ADR-RN-009 to ADR-RN-012, which remain Proposed, and it authorizes no gate beyond A.
- **Gas rules can change.** A later Ethereum fork may reprice calldata. Gas use must be confirmed
  with `eth_estimateGas` before signing, and the 30,000 limit re-checked.
- **What the anchor shows.** As ADR-RN-012 allows, the anchors show the same commitment payload
  in the data reported for both networks. They say nothing about whether the synthetic evidence is
  true. `CHAIN_PROVEN` is still never produced.

## Amendment C1 (Accepted, offline implementation only): XRPL expiry offset and submission margin

- Status: **Accepted for the reviewed offline implementation only** (RN-NET-03B2-C6-PREP
  governance closure; the implementation is RN-NET-03B2-C3, PR #26, squash-merged as main
  `1723439`, whose tree `a91fc55` equals the reviewed head `578a4db`). It authorizes none of
  gates B to F. See *What this acceptance covers* at the end of this amendment.
- The sequence it required is complete:
  - **It stayed Proposed until C3 implemented it.** That meant the offset constant, the Python
    preparation reference, the specification text and the regenerated B2 fixtures and digests,
    with tests showing `+ 80` binding and the refusal when 4 or fewer remain (PR #26).
  - **Then it needed an independent review.** PR #26's review was PASS WITH NON-BLOCKING
    FOLLOW-UPS; all four follow-ups were fixed and a focused re-check closed them before merge.
- Founder decision behind it (2026-11-02): draft a proposal raising the offset from 20 to 80
  validated ledgers, and keep the broadcaster's refusal when four or fewer ledgers remain. This
  is a testnet execution proposal. It does not authorize signing or broadcasting.
- Readiness analysis: [RN-NET-03B2-C operational readiness](../genesis/rn-net-03b2c-operational-readiness.md) §2.

### Why

Decision §1 sets `LastLedgerSequence` = the latest validated ledger + 20. XRPL closes a ledger
every 3 to 5 s, so the transaction is valid for about 60 to 100 s after preparation. ADR-RN-019
§5 also voids the broadcast authorization once 4 or fewer ledgers remain, leaving about 48 to
80 s. Every step after preparation must fit in that time:

1. the founder reviews the printed intent and approves it by digest (gate D);
2. the passphrase prompt and the scrypt key derivation;
3. one signature, the signer's self-check and the two verifications;
4. the founder writes the `rnnet.broadcast-authorization.v1`. It binds the blob SHA-256 and the
   transaction hash, so it cannot be written before signing;
5. the broadcaster's own two verifications and its 6 pre-submit reads, then the submission.

That does not fit reliably with a person at every step. An expired attempt is safe (nothing is
sent once the authorization is void), but it is slow: the signer's sign log then refuses a
second signature for that `Sequence` until a status check past `LastLedgerSequence` records the
first transaction as absent (ADR-RN-019 §8), and a new gate D follows.

### Proposed change

1. **Offset.** `LastLedgerSequence` = the **lowest** validated ledger reported by the
   preparation providers + **80** (ADR-RN-018 §5 binding, with 80 in place of 20).
2. **Submission margin, unchanged.** The broadcaster refuses, before any write, once a validated
   ledger it reads satisfies `LastLedgerSequence` − ledger ≤ 4 (ADR-RN-019 §5 and the code's
   `validatedLedger >= lastLedgerSequence - 4`). So at least 5 ledgers must remain at the
   pre-submit read. The amendment to ADR-RN-019 corrects §6's wording to match.
3. **Testnet only, no format change.** `LastLedgerSequence` is already an intent field, bound at
   gate D and covered by the intent digest. The ADR-RN-016 check accepts any `UInt32` value, so
   neither the check, the intent format, the payload nor any commitment changes.
4. **What changes in code, in a later reviewed PR (C3), not here:** `XRPL.lastLedgerOffset` in
   `packages/tx-intent/src/genesis.mjs`, the `+ 20` in
   `tools/reference/rnnet_prep_reference.py`, `spec/rnnet.tx-preparation.v1.md` §5 (binding and
   the overflow case, which becomes "within 80 of 2^32−1"), the preflight template text, and the
   B2 fixtures and expected intent digests that follow from them. Until that PR merges, the code
   still binds + 20.

### Window it gives

| | Ledgers | At 3 s | At 4 s | At 5 s |
|---|---|---|---|---|
| Offset from the lowest provider's validated ledger | 80 | 240 s | 320 s | 400 s |
| Worst case, measured from the highest provider (4-ledger skew, ADR-RN-018 §4) | 76 | 228 s | 304 s | 380 s |
| Usable before the authorization is void (≤ 4 left refused) | 72 | 216 s | 288 s | 360 s |
| Left for the submission itself after the last pre-submit read | ≥ 5 | ≥ 15 s | ≥ 20 s | ≥ 25 s |

### Consequences

- **Feasible, with conditions.** About 3.6 minutes in the worst case is enough for the steps above
  only if:
  - the founder does not type the authorization fields by hand; tooling prints a draft with
    the recomputed digests for the founder to check and save (ADR-RN-019 Amendment C1, E3; readiness §8);
  - the sequence is rehearsed end to end against simulated providers first, with timings;
  - D-XRPL and E-XRPL run in one sitting, on one machine, with the WSL clock checked.
- **No added risk.** XRPL sets no upper bound on `LastLedgerSequence`. A longer window:
  - lets a queued transaction be included later, not earlier;
  - does not let the transaction move value (a zero-value `AccountSet`);
  - delays the earliest expiry finding by about 4 to 5 minutes.
- **Mainnet replay, unchanged in practice.** Replay needs a Mainnet account with the signed
  `Sequence` and a Mainnet ledger at or below `LastLedgerSequence` (signing design §8). The
  Testnet ledger index (21,917,563 at SMOKE-01) is far below Mainnet's, so a 60-ledger change
  does not alter that. This is a stated assumption: RN-NET has no reviewed Mainnet provider and
  makes no Mainnet read.
- **Unchanged:** the fee (12 drops, cap 1,000), the key, the memo, `Sequence` handling, and every
  gate.

### C3 implementation record (RN-NET-03B2-C3)

At C3 this amendment stayed **Proposed**. RN-NET-03B2-C3 implemented it offline and recorded what
was built; that record accepted nothing and authorized nothing. The code binds `+ 80` from this merge on, as the
amendment's own sequence requires (implementation, then review, then acceptance). No run can bind
it live: every live entry point is disabled, and gate D still needs this amendment accepted.
- **The offset.** `XRPL.lastLedgerOffset` is 80 (`packages/tx-intent/src/genesis.mjs`), and the
  Python preparation reference binds `+ 80` (`XRPL_LAST_LEDGER_OFFSET`).
- **Documents.** `spec/rnnet.tx-preparation.v1.md` §5 binds `+ 80` and states the overflow case
  "within 80 of 2^32−1". The preflight template reads "lowest validated ledger of the two
  providers + 80".
- **Fixtures.** The B2 fixtures were regenerated (`rnnet.preparation-b2-fixtures.v2`). Their XRPL
  exchanges are unchanged, so each accepted XRPL intent differs from its B2 version only by
  `LastLedgerSequence` (+ 60). The Python reference reproduces every digest.
- **Unchanged.** The submission margin (refusal once 4 or fewer remain), the fee, the memo, the
  42-byte payload and the Genesis commitment. `fixtures/genesis-proof-01` is immutable and
  byte-identical: its preflight rehearsal keeps the recorded offset 20
  (`PREFLIGHT_LAST_LEDGER_OFFSET`), pinned by a test next to `XRPL.lastLedgerOffset` = 80.
- **The window, rehearsed offline** (`fixtures/rehearsal-c3`). The latest gate-D review that still
  submits, with every other step at its nominal time:
  - 148 s at 3 s per ledger;
  - 222 s at 4 s per ledger;
  - 297 s at 5 s per ledger.

  The run then submits with exactly 5 ledgers left; one second more leaves 4, and the broadcaster
  refuses before any write.

### What this acceptance covers, and what it does not

| Decision | Status | What it allows |
|---|---|---|
| **Acceptance of the offline implementation** (this amendment) | **Accepted**, for the code reviewed in PR #26 as merged | `LastLedgerSequence` = the lowest provider's validated ledger + 80, as bound by `XRPL.lastLedgerOffset` in `packages/tx-intent`, the Python preparation reference, `spec/rnnet.tx-preparation.v1.md` §5, the preflight template and the regenerated B2 fixtures; the unchanged submission margin (refusal once 4 or fewer ledgers remain); the offline rehearsal timings in `fixtures/rehearsal-c3` |
| **Any live use of the `+ 80` rule** | **Not authorized** | A live XRPL preparation run (gate D's reads, H6), signing it (D-XRPL) and submitting it (E-XRPL), each by its own founder decision |

- **Scope.** The acceptance covers the behaviour as implemented and reviewed: the offset value,
  the margin and the code, documents and fixtures listed above. It does not cover a different
  offset, a different margin or any later change to them, which need a new amendment.
- **The live entry points stay disabled.** `tools/prepare/prepare-live.mjs` and
  `tools/submit/submit-anchor.mjs` refuse as commands; enabling either is a separately reviewed
  change, not this acceptance.
- **Still separately authorized, and not authorized by this acceptance.** Each needs its own
  written founder decision, as the readiness analysis §8 and §9 list:
  - **live RPC**: any request to a provider, including the C6 compatibility run (H3) and every
    preparation run (H6), each with its own read authorization and exact budget;
  - **operational key generation** (gate B, H4);
  - **funding** (gate C, H5);
  - **operational signing** (gate D, H7);
  - **broadcasting** (gate E, H8 and H9);
  - **public evidence publication** (gate F, H10).
- **Unchanged:** `fixtures/genesis-proof-01` (its preflight keeps the recorded offset 20), the
  fee, the memo, the payload and the Genesis commitment.
- **Not covered:** ADR-RN-019 Amendment C1 (live entry points) stays **Proposed**.
